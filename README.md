# YouTube copy

Модульный монолит видеосервиса. Реализованы Compose-инфраструктура, предметная
схема PostgreSQL, аккаунты, каналы и загрузка оригиналов в закрытое S3.
Обработка видео и воспроизведение добавляются следующими пунктами `TODO.md`.

## Локальная подготовка

Требуется Python 3.12–3.14 и `uv`.

```bash
uv sync --extra dev --frozen
cp .env.example .env
```

Файл `.env.example` не содержит рабочих секретов. Health endpoint проверяет только
процесс; аккаунтам и загрузке нужны PostgreSQL и Garage.

## Запуск

```bash
uv run youtube-web
curl http://127.0.0.1:8000/healthz
```

Точка входа будущего фонового процесса проверяется отдельно:

```bash
uv run youtube-worker
```

## Проверки качества

```bash
uv run ruff check .
uv run ruff format --check .
uv run pytest
```

Интеграционные тесты схемы требуют отдельную одноразовую PostgreSQL-БД, имя которой
оканчивается на `_test`. Тесты сами выполняют циклы миграций `base → head` и
`0001 → head`, поэтому их нельзя направлять на рабочую БД:

```bash
YOUTUBE_RUN_POSTGRES_TESTS=1 \
YOUTUBE_DATABASE_URL=postgresql+asyncpg://youtube@localhost:5432/youtube_test \
YOUTUBE_DATABASE_PASSWORD_FILE=/path/to/test-password \
uv run pytest tests/test_database_schema.py
```

S3-реквизиты можно задать парой переменных `YOUTUBE_S3_ACCESS_KEY_ID` и
`YOUTUBE_S3_SECRET_ACCESS_KEY`, но в Compose они должны поступать через защищённые файлы,
указанные в `YOUTUBE_S3_ACCESS_KEY_FILE` и `YOUTUBE_S3_SECRET_KEY_FILE`. Контейнер
`garage-init` использует настройки зоны, ёмкости, имени ключа, бакета и ограниченного
таймаута из `.env.example`; ручные команды инициализации не входят в штатный запуск.

## Docker Compose

Для локального инфраструктурного запуска нужны Docker с Compose plugin и OpenSSL.
Сначала создайте игнорируемые Git локальные секреты, затем поднимите стек:

```bash
scripts/prepare-runtime-secrets.sh
docker compose up --build -d
docker compose ps -a
curl http://127.0.0.1:8080/healthz
```

Наружу публикуется только Nginx на порту `8080`. PostgreSQL, S3/RPC/admin Garage и
приложение доступны только во внутренней Docker-сети. `garage-init` автоматически
назначает и применяет односерверный layout, создаёт закрытый бакет и ключ только с
read/write, сохраняет реквизиты в отдельный том и проверяет HEAD/PUT/GET/Range/DELETE.
Повторный `docker compose up -d` перепроверяет фактическое состояние без смены ключа.
Тот же скрипт создаёт отдельный `app-secret` для HMAC-подписи CSRF-токенов; он передаётся
приложению как Docker secret и не попадает в Git или логи.

## API аккаунтов и каналов

Доступны `/api/v1/auth/csrf`, `register`, `login`, `logout`, `me`, публичный
`/api/v1/channels/{handle}`, редактирование своего канала и административная
смена роли/активности. Изменяющие запросы требуют cookie и заголовок `X-CSRF-Token`,
а также `Origin`, точно совпадающий с `YOUTUBE_PUBLIC_ORIGIN`. Для HTTPS нужно включить
`YOUTUBE_COOKIE_SECURE=true`; текущий Compose использует явно обозначенный локальный HTTP-режим.

## Загрузка видео

После входа в том же браузере откройте `http://localhost:8080/upload`.
Страница принимает название, описание, видимость и файл, показывает прогресс XHR,
позволяет отменить передачу и опрашивает статус после приёма. Экраны входа и
регистрации появятся в пункте 11; пока доступны API аккаунтов и `/docs`.

Контракт API:

1. `POST /api/v1/videos` с JSON `{ "title": "Видео", "description": "", "visibility": "private" }`
   создаёт черновик. Видимость по умолчанию private; owner/channel/status задать нельзя.
2. `POST /api/v1/videos/{id}/upload` принимает **сырые байты файла** с
   `Content-Type: application/octet-stream`, cookie, `Origin` и `X-CSRF-Token`.
   Multipart/form-data и Content-Encoding не принимаются. Длина может быть неизвестна:
   лимит проверяется по фактическим байтам, заявленная длина при наличии сверяется.
   Имя и MIME исходного файла не используются как путь или доказательство формата.
3. `202` означает: оригинал записан в S3, asset и transcode-job сохранены одной
   транзакцией. `GET /api/v1/videos/{id}/status` доступен только владельцу и не
   раскрывает ключи S3. Модератор и администратор не получают чужие метаданные.

До пункта 9 worker не обрабатывает задания: принятые видео остаются в `processing`.
FFprobe проверит фактический формат, видеопоток и длительность именно на этом шаге.

По умолчанию максимум — 500 МиБ, два одновременных приёма на процесс, резерв свободного
диска — 128 МиБ; переменные `YOUTUBE_UPLOAD_*` перечислены в `.env.example`.
В Compose значения заданы в `x-app-environment`; при увеличении размера согласуйте
`client_max_body_size` Nginx (сейчас 502 МиБ). Nginx не буферизует тело на диск.
На временном диске web должно быть свободно не менее размера допускаемого файла плюс
резерв; при нескольких загрузках резервирование консервативно учитывает все слоты.
Приём ограничен часом и 60 секундами простоя между порциями. Создание черновиков и
попытки передачи независимо ограничены десятью запросами в час на аккаунт.
Ограничения слотов и частоты рассчитаны на **один web-процесс**, сбрасываются при
перезапуске; перед масштабированием их нужно сделать общими.

Временные файлы создаются без доступного имени, удаляются при закрытии и остановке
процесса. Запись/хеширование идёт блоками до 256 КиБ в потоке, S3 использует
последовательные части по 8 МиБ; полный файл не собирается в RAM. Транзакции БД и
блокировки строк не удерживаются во время чтения тела или обращения к S3.

Ошибки возвращаются безопасными кодами: 400 — пустой/прерванный/несогласованный запрос,
408 — таймаут, 413 — размер, 415 — транспортный формат, 409 — состояние,
429 — частота, 503 — занятые слоты или S3, 507 — временный диск.
Прерванная передача переводит запись в `failed`; владелец может повторить её с новым
upload_id. Завершение повторно проверяет сессию и активность аккаунта. Отмена после
того, как сервер уже принял все байты, не гарантирует отмену сохранения/обработки.

Аварийное завершение процесса или потеря БД может оставить `uploading`, незавершённый
S3 multipart либо объект без ссылки из БД. Восстановление этих состояний, очистка
сирот и старых поколений после защитного периода относятся к пункту 9. При
неопределённом результате коммита объект не удаляется, чтобы не повредить уже
зафиксированное задание. Payload transcode-job содержит `upload_id`; worker должен
сверять его с текущим поколением видео.

## Интеграционные проверки загрузки

Тесты используют отдельную **одноразовую** БД `youtube_test` и существующий закрытый
бакет Garage. Проверка S3 удаляет только свой случайный тестовый объект. Первый раз
создайте тестовую БД (если она уже существует, повторять создание не нужно):

```bash
docker compose exec -T postgres createdb -U youtube youtube_test
```

Затем выполните проверки. Миграционный fixture пересоздаёт схему только тестовой БД:

```bash
docker compose -f compose.yaml -f tests/compose/integration.yaml build tests
docker compose -f compose.yaml -f tests/compose/integration.yaml run --rm --no-deps tests
```

Тестовый образ содержит фиксированные dev-зависимости. Покрыты успешная передача,
реальный S3 multipart/анонимный отказ, права и CSRF, ложный Content-Length,
лимиты диска/байтов/частоты, конкуренция, отмена, таймаут, повторная попытка,
выход из аккаунта во время передачи и атомарность передачи задания в обработку.

## Остановка

Остановить контейнеры без потери данных:

```bash
docker compose down
```

Не добавляйте `-v`: эта опция удалит постоянные тома PostgreSQL, Garage и реквизитов.
