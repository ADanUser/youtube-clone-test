# Деплой и эксплуатация

## Требования и режимы

Целевая система — чистая Ubuntu 24.04 LTS x86_64 с 2 CPU, 4 ГиБ RAM,
20 ГиБ свободного диска и доступом в интернет. Скрипт устанавливает Docker Engine,
Compose plugin, OpenSSL, Nginx и Certbot из официальных репозиториев. Повторный запуск
не удаляет тома, сохраняет созданные секреты и S3-ключ и повторно применяет только
нужные миграции и идемпотентный seed.

Тестовый HTTP по IP:

```bash
sudo YOUTUBE_PUBLIC_IP=203.0.113.10 bash scripts/deploy.sh
```

Если `YOUTUBE_PUBLIC_IP` не задан, скрипт использует первый адрес `hostname -I`.
Открывается `http://IP:8080`; cookie намеренно создаются без `Secure`. Этот режим
не предназначен для публичной эксплуатации.

HTTPS по домену (DNS A/AAAA уже указывает на сервер, входящие 80/443 открыты):

```bash
sudo YOUTUBE_DOMAIN=video.example.org \
  YOUTUBE_TLS_EMAIL=admin@example.org \
  bash scripts/deploy.sh
```

В этом режиме Compose слушает только `127.0.0.1:8080`, системный Nginx проксирует
приложение, а Certbot получает сертификат, включает редирект HTTP → HTTPS и продление.
Cookie получают `Secure=true`. Ошибка сертификата останавливает деплой: автоматического
перехода к открытому HTTP нет. Смена уже выбранного режима меняет публичный origin и
может сделать прежние браузерные сессии непригодными.

Скрипт запускают из распакованного репозитория. Он проверяет Compose-конфигурацию,
создаёт секреты в `.runtime/secrets` с правами `0600`, последовательно выполняет
Garage init, Alembic, web/worker и seed, затем проверяет `/healthz`. Ни скрипт, ни
обычные логи не выводят значения секретов. Демо-пароли читаются только явной командой:

```bash
sudo docker compose --env-file .runtime/deploy.env run --rm --no-deps \
  --entrypoint cat seed /run/youtube-demo/credentials
```

## Состояние и логи

Все команды выполняются из корня репозитория:

```bash
sudo docker compose --env-file .runtime/deploy.env ps -a
sudo docker compose --env-file .runtime/deploy.env logs --since=30m web worker nginx
curl --fail "$(sudo sed -n 's/^YOUTUBE_PUBLIC_ORIGIN=//p' .runtime/deploy.env)/healthz"
df -h
```

Для остановки без потери данных используйте `docker compose ... down`. Никогда не
добавляйте `-v`: эта опция удаляет PostgreSQL, видео, S3-реквизиты и демо-пароли.
Compose ограничивает JSON-логи каждого контейнера пятью файлами по 10 МиБ. На сервере
следует контролировать заполнение диска, возраст очереди и `failed` jobs, ошибки
web/worker, доступность `/healthz` и срок TLS-сертификата.

## Согласованный бэкап

Простое копирование работающих Docker volumes не является согласованным бэкапом.
На время снимка включите окно обслуживания: остановите внешний Nginx или закройте
входящий трафик, затем остановите web и worker. Сохраните:

1. PostgreSQL через `pg_dump` в custom format.
2. Именованные volumes Garage `garage_meta`, `garage_data` и `s3_credentials` после
   остановки Garage.
3. `.runtime/secrets`, `.runtime/deploy.env`, Compose-файлы и TLS-материалы системного
   Nginx/Certbot при HTTPS.

Архив шифруют и хранят отдельно от сервера. Имена volumes включают Compose project;
получите точные имена через `docker volume ls` и не подставляйте их вслепую. После
снимка сначала запустите Garage/PostgreSQL, затем повторно выполните deploy-скрипт.

## Восстановление

Восстанавливайте сначала на отдельном сервере той же версии проекта. До запуска
приложения верните `.runtime` с исходными правами, volumes Garage и S3-реквизитов,
создайте пустую PostgreSQL-БД и загрузите `pg_restore`. Затем запустите deploy-скрипт:
он проверит Garage, применит только новые миграции и дождётся сервисов.

Проверка восстановления обязательна: версия Alembic на `head`, вход демо-пользователя,
видимость public/private/hidden, чтение и перемотка видео, новое создание/обработка
ролика и неизменность S3 access key. Рабочий сервер не переключают на восстановленную
копию до прохождения этих проверок. Разрушительные миграции и удаление томов требуют
отдельного разрешения и предварительно проверенного бэкапа.
